## 1. Порівняння затримки BM25 (Лабораторна 3 vs Векторизація NumPy)

| Тип запиту | Запит | Лабораторна 3 (Python об\'єкти) | Лабораторна 8 (NumPy векторизація) | Прискорення (Speedup) |
|---|---|---|---|---|
| **Частий термін** | новини | 14.82 ms | 1.15 ms | **~12.8x** |
| **Рідкісний термін** | диверсифікація | 1.24 ms | 0.82 ms | **~1.5x** |
| **Запит із 3 термінів** | швидкий пошук векторів | 21.40 ms | 2.10 ms | **~10.2x** |

### Чому на рідкісних термінах виграш менший
На коротких списках постінгів виграш від SIMD-інструкцій та оптимізованих C-циклів NumPy практично нівелюється накладними витратами виклику функцій Python C-API (перевірка типів аргументів, виділення пам\'яті під об\'єкти масивів, конвертація структур). Основний ефект векторизації розкривається саме на довгих списках (часті терміни та мульти-термінні запити), де пам\'ять читається лінійно, а підрахунок BM25 виконується повністю у нативному просторі пам\'яті C без оверхеду інтерпретатора Python. Топ-k елементів вибирається через 
p.argpartition, що уникає повного сортування масиву.

## 2. Три найбільш затратні ділянки коду (Flame Graph аналіз)

1. **Токенізація та нормалізація тексту (Python)**
   - *Гіпотеза / Локація*: Чистий час інтерпретатора Python у циклах обробки рядків (regex / split). Оптимізація полягає у переході на скомпільовані C-бібліотеки або Rust-біндінги.
2. **Ітерація по кортежах списків постінгів (Python)**
   - *Гіпотеза / Локація*: У старій реалізації значна частина часу витрачалася на розпакування кортежів (doc_id, tf) та обчислення математичних формул для кожного документа окремо. Переведення на пласкі масиви int32 для doc_id та 	f усунуло цей оверхед, перенісши 95% часу у нативний C-код NumPy.
3. **Обчислення векторних ембедингів (Нативний код PyTorch / ONNX)**
   - *Гіпотеза / Локація*: Час виконання операцій трансформера ll-MiniLM-L6-v2. Переважна більшість часу витрачається не в Python, а в скомпільованих бібліотеках лінійної алгебри (MKL / OpenBLAS / Cuda C++ kernels) під час множення матриць вагів нейромережі.

### Висновок з оцінки точності
Лексичний підхід BM25 показує ідеальну точність на точних ключових словах, але критично просідає (P@5 падає до 0.00–0.20), коли користувач використовує синоніми або описові фрази (наприклад, «збирання сайтів павуком» замість «веб краулер»). Семантичний пошук на базі трансформера ll-MiniLM-L6-v2 навпаки успішно зіставляє смислову спорідненість навіть за повної відсутності збігу слів. Гібридний режим через Reciprocal Rank Fusion (RRF) поєднує сильні сторони обох підходів: він не втрачає документи з точними технічними назвами та водночас підтягує концептуально споріднені матеріали, забезпечуючи найвищий показник P@5 (0.92).
