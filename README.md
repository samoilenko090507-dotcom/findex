# findex – Лабораторна робота 4: Типи, тести, пакування і CLI

У межах проєкту реалізовано інвертований індекс із підтримкою протоколу Mapping, ранжуванням за моделями TF-IDF та BM25, синтаксичним парсером запитів і повноцінним CLI-інтерфейсом.

## Демонстрація роботи CLI

Побудова двійкового індексу з позиціями виконується командою:
`python -m findex.index data/ --out index.bin`

Ранжований пошук із виділенням сніпетів та моделлю BM25 запускається так:
`python -m findex.search index.bin "project gutenberg" --scorer bm25 --top 3`

## Санітарні перевірки та оцінка якості

Математична модель BM25 коректно відпрацьовує базові перевірки на проіндексованому корпусі документів. Рідкісні терміни отримують вищу вагу через компонент IDF, що робить їх більш інформативними порівняно з частими словами. Закон спадної віддачі також працює правильно, не дозволяючи штучно накручувати релевантність багаторазовим спамом одного слова в тексті. Окрім цього, модель успішно нормалізує бали за довжиною документа, віддаючи перевагу коротшим текстам за однакової кількості входжень шуканого слова. Обидві моделі демонструють стабільну точність на тестових запитах, проте BM25 суттєвіше штрафує надмірно довгі тексти та краще усуває аномалії частотності слів.

## Тестування та покриття

Покриття проєкту тестами становить 55 відсотків. Поза тестами свідомо залишено допоміжні скрипти завантаження даних та експериментальні бенчмарки, оскільки вони не є частиною основного пошукового рушія індексатора.

### Експеримент із безгіловою збіркою (Python 3.13t)
Перевірка стану блокування: `sys._is_gil_enabled() -> False`. На Windows запуск сторонніх C-бібліотек (зокрема залежностей для побудови графіків) під версією 3.13t вимагає ручного збирання з вихідного коду (MSVC), оскільки готові бінарні пакети ще відсутні в екосистемі.

### Аналіз результатів та поведінки GIL
Потоки (threading) через блокування інтерпретатора GIL не демонструють масштабування на CPU-bound задачах і просідають через постійні накладні витрати на перемикання контексту. Багатопроцесорність показує реальне падіння сумарного процесорного часу (CPU time з 3.95s до 1.39s), що свідчить про ефективний паралельний розподіл обчислень між ядрами. Водночас у системі Windows метод створення процесів spawn спричиняє відчутні витрати на повторну ініціалізацію інтерпретатора та серіалізацію даних, через що загальний реальний час (Wall time) суттєво не виграє відповідно до закону Амдала.

### Reflection та відповіді на питання

Для задач вигрібання мережі асинхронний підхід на 20 одночасних з'єднань в одному потоці значно ефективніший за багатопроцесорність з лаби 5, оскільки краулер 99% часу проводить в очікуванні відповіді віддаленого сервера. На відміну від процесів, які вимагають копіювання пам'яті, важкого перемикання контексту ядра ОС та серіалізації даних через IPC, легковагі корутини asyncio займають лише кілобайти оперативної пам'яті і практично безкоштовно перемикаються подіями сокетів.

Ліміт на хост (`per_host_delay = 0.5s`) обмежує пікову пропускну здатність на одному домені до двох запитів на секунду, тому час збору 155 сторінок на 5 та 20 потоках однаковий. Проте цей ліміт критично необхідний: без нього краулер влаштував би неетичну DoS-атаку на навчальний сервер, отримав би статус 429 Too Many Requests або бан IP-адреси.

Якби важка синхронна індексація з лаби 1 або парсинг через CPU-bound операції запускалися безпосередньо всередині корутини без `run_in_executor` чи окремої черги, цикл подій Python повністю зупинився б на час побудови індексу, заблокувавши обробку мережевих пакетів для решти 19 з'єднань і викликавши масові таймаути в мережі.
